# 论LLM大模型在软件测试中的应用

**摘要**

2024年12月至2026年2月，我作为系统分析师，参与了某主机厂整车动力学与自动驾驶联合仿真平台（VDSP）的建设。平台把车辆动力学、交通场景、传感器与规控算法按标准接口组装成仿真链路，并与Simulink构件库、自研C++库及Autoware组件集成。一期约十四个月交付，覆盖五个车型平台和六类驾驶工况。

本文结合该平台测试体系的落地，论述大语言模型在软件测试中的应用。文中先说明测试用例生成应采用上下文装配、分层提示、结构化产出和执行回放相结合的方式；再以单元、集成、系统三条测试线索，说明如何把模型约束在配置与数据生成上，并用工具调用和黄金样本抑制幻觉；最后分析效率收益，以及冗余代码、上下文偏差和物理误判的治理措施。

电动化与智能化压缩了整车开发周期，GB/T 41798等标准又要求覆盖更多极限工况和长尾场景，传统样车试验成本高、窗口短，难以在概念设计阶段评估操稳、舒适性与规控效果。同时，规控算法与车型强绑定，质量、轴距和悬架特性一变，仿真结论便不能直接复用。主机厂迫切需要一套可配置、可复用的联合仿真环境，把动力学、传感器与规控放在同一条链路上反复试算，用数字样机替代部分实车试验，把验证活动前移到设计早期。

针对上述矛盾，我们建设了VDSP平台。平台分为四层：功能模型层提供积分求解器、坐标变换和物理引擎，并组装轮胎魔术公式、非线性悬架、转向机构和动力总成等子模型；整车耦合层按FMI标准将子构件封装为FMU，用图结构描述端口连接并自动推导计算顺序；规控接入层采用端口适配器，屏蔽Autoware、ROS在消息与生命周期上的差异；工况与后处理层把路测数据整理为标准激励，批量回放并生成报告。工程以XML保存组装关系，以CSV承载激励，前端用可视化画布完成拖拽连线，运行前由静态规则校验端口因果性与未连接输入。我主要承担接口契约、图组装方案和测试流水线的分析与实现，使同一套链路能够较快切换车型与工况。

利用大语言模型生成测试用例，关键不在任其自由编写脚本，而在把生成过程设计成可约束、可检查的流水线。一般包含四个环节：将被测对象的功能说明、端口契约（信号名、单位、采样率、初始化顺序）和少量正反例注入提示，避免膻造接口；按层次设计提示，单元测试侧重输入空间与边界值，集成测试侧重连接关系与时序，系统测试侧重场景切片与数据清洗；约束模型只产出XML、CSV等结构化结果，以便校验器按模式检查；再以运行日志和断言构成生成与回放闭环，修正漏测与误测。与此同时必须承认，模型存在幻觉、输出不稳定和对领域物理规律掌握不足等问题，生成结果需经规则校验和工程师抽检后才能入库。这一实现方式，构成了VDSP测试工作中应用大模型的基本方法。

在利用大语言模型辅助车辆动力学测试的过程中，我们让模型承担子功能模块的用例生成任务，而不是直接改写求解器代码。实践中很快发现，轮胎、悬架、转向等子功能的输入输出结构差异很大，功能组装又会不断衍生新的测试场景，模型针对每个单点需求独立生成脚本时，缺乏对整体架构的归纳，往往重复制造结构相似的适配器和中间件，代码库迅速膨胀，版本管理和回归验证都变得困难。针对这一问题，团队参考Simulink的模型连接方式，将模块间关系从代码层上浮到配置层：各子功能遵循统一端口规范，运行时通过XML解析每条数据边，自动推导依赖并决定执行顺序，模型只需生成描述连接关系的配置，不再产出胶水代码。与此同时，我们构建了基于CSV的通用数据源构件，内置数值积分与插值，按多维矩阵自动推导逐步输出，模型仅需按规范生成对应的激励文件。XML与CSV作为结构化文本纳入配置库统一管理，同一套图结构即可覆盖不同子功能的灵活测试，单元级从构造到批量执行由数日缩短到小时量级。

当测试从单模块走向整车组装，大模型的上下文能力成为新的约束。渲染采用左手系、规控采用Frenet、整车定位采用UTM、零件采用局部车体坐标系，单位、偏移和采样率在端口之间必须显式转换。若指望模型靠通读多层代码来拼出测试脚本，压缩后的上下文很容易写错变换链，人工返工反而拖慢进度。我们将坐标与单位变换从让模型推理改为让模型调用工具：用C++实现可根据端口契约自动推导变换的构件，并把使用说明作为可调用技能注入会话，模型只需给出源坐标系、目标坐标系和信号列表。工程本身以XML保存，连线还区分初始化与运行时相位，增益和时序也可配置；连接合法性、因果性冲突和未连接输入由静态校验在运行前拦截，诊断按错误、警告分级后回灌给模型作为修正提示。可视化画布上可按端口高亮相关边，便于对照校验报告定位。这样既缩短了无效推理，也把接口细节从自然语言幻觉中抽离出来，坐标类脚本错误明显下降，生成速度同步提高。

在系统测试层面，主机厂提供了充足路测数据，缺的不是样本而是可用样本。原始记录中夹杂噪声、无效片段和与当前验证目标无关的通道，人工清洗成本很高。我们让模型按工况标签、通道字典和被测功能对齐规则清理数据，批量生成系统级激励，并在后处理层回放、出报告。路测轨迹涉及实车状态，生成任务一律在内网私有化环境完成，避免原始数据出域。这一做法显著加快了覆盖，却也暴露了模型对车辆物理判断的短板：高速过弯、单轮驱动不足等失稳工况下程序仍在运行，真正要识别的是传感器组合所表征的失稳模式。工程师看侧偏角与轮速差即可判断打滑，模型却可能判为正常。我们没有用模型替换工程师，而是由其筛选稳态与失稳态边界样本作为黄金标准注入提示，模型只在该邻域内做回归比对，越界结果必须人工确认。由此，测试从生成即采用转为约束生成、工具校验、黄金样本锚定。一期交付后，动力学相关集成缺陷约下降四成，单模块从用例构造到批量验证可在八小时内完成。

回顾VDSP一期建设，我更深切体会到：复杂仿真系统的关键不在堆砌模型，而在把接口、调度和验证做成可配置的基础设施。FMI封装使Simulink、C++求解器和规控中间件能在同一张图上协作；连接关系上浮到XML，使车型切换更多地变成改配置；激励标准化为CSV，使工况库可以积累和复用。作为系统分析师，我在需求到契约、契约到组装、组装到回归这条链路上反复权衡，也认识到可视化编排与静态校验对跨团队协作的价值，问题能够定位到端口和量纲，而不是停留在口头争执。这使我对用结构约束复杂度有了可操作的认识。

当然，一期仍有不足。多车型共用同一套子模型时，整备质量、转动惯量和衬套刚度等参数仍主要靠资深工程师手调，尚未形成可检索的参数推荐库，换型前期仍需一两天的标定成本。画布在模块数量上百以后，自动布局与连线高亮会变得迟滞，计划用分层子图和按需渲染来控制交互复杂度。此外，部分第三方求解器的小版本差异会改变步长和初始化顺序，目前依靠适配表手工维护。下一步拟建立车型参数主题库，把标定记录结构化以便复用；对超大规模工程启用子系统级封装，缩小单张画布的节点规模；并以版本矩阵自动选择适配器。这些改进并不动摇既有交付，却能使后续车型接入更加平稳。
