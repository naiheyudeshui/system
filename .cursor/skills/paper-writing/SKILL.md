# 论文写作指导 Skill

## 目标

把用户的真实项目经验和系统分析师知识，组织成可验证、可评分、像工程师亲自实施过的论文。输出应同时满足：题目覆盖完整、论点前后一致、技术选择有理由、实施过程可复述、效果与局限可信。

本 skill 服务于“指导、提纲、起草、改写、批改、模拟评分”，不是把已有两篇 LLM 文章当作范文照抄。它们只能作为案例素材和反面校正材料。

## 仓库资料与使用顺序

先检查文件和 Git 状态，保留用户已有改动。默认资料位置：

- `论文/论文写作总复习资料（第二版）.pdf`：论文结构、审题、段落和评分导向。
- `系统分析师-一本通精华知识点-第二版(OCR).docx/pdf`：架构、需求、质量、测试、数据、项目管理等知识点的定义、关系、优缺点和适用场景。
- `系统分析师-案例分析总复习资料-第二版(OCR).pdf`：场景化分析、问题定位、方案取舍、风险与效果的案例表达。
- `论文/系统分析师论文范文/`：观察常见叙事结构和篇幅，不复制事实。
- `论文/论LLM大模型在软件测试中的应用.md`、`论文/论LLM大模型在软件测试中的应用-平台架构版.md`：用户既已说明不是完全范文，只可用于了解 VDSP/HSIM 项目事实、识别可改进处。
- `论文/HSIM系统架构分析.md`：工程背景、架构边界、接口、调度、仿真、控制与验证事实。

需要书上知识时，先定位主题和页码/章节，再核对原文；OCR 不清、版本冲突或无法确认的内容标为待核实，不得把猜测写成教材原话。

## 工作流

1. **审题**：拆出主题、限定词、三个子问题、必须出现的技术动作和结果。建立“题目要求 → 论文段落 → 证据”矩阵。
2. **盘点项目**：只采用用户提供或仓库可核对的事实。整理背景、痛点、角色、约束、方案、实施、验证、效果、问题和改进；缺事实时用占位符并明确询问。
3. **选主线**：全文围绕一个矛盾和一条闭环展开，例如“复杂系统集成困难 → 配置化架构与契约约束 → 自动验证与回放 → 指标改善”。不要把多个项目拼成流水账。
4. **搭提纲**：推荐“摘要/背景 → 项目与问题 → 架构或方法 → 关键实施（按子问题分段） → 测试与效果 → 局限和改进 → 结语”。考试正文通常不使用章节标题，按自然段完成结构。
5. **写段落**：每段遵循“结论/做法 → 原因 → 落地细节 → 验证或结果 → 边界”。优先写我负责的决策与动作，少写职责清单。
6. **复核**：逐题回填矩阵；检查术语、接口、数据流、时间顺序、数字、角色、项目名称一致；删除无证据的夸张收益。

## 系统分析师知识如何写进论文

书本知识必须转译为“项目中的选择”，而不是背定义：

- **定义**：用一句准确、短的概念说明建立共同语境。
- **问题映射**：说明项目中哪个现象对应该知识点。
- **决策**：写为何选择该方法/架构，以及放弃了什么替代方案。
- **落地**：给出组件、接口、数据、流程、约束、工具或责任边界。
- **验证**：说明如何测试、检查、度量、回放或审计。
- **边界**：写适用条件、代价、风险和后续改进。

推荐句式：

> 按照【知识点】的原则，项目将【问题】拆分为【机制】；我选择【方案】是因为【约束/权衡】，并通过【验证方式】确认【结果】。

不要堆砌“高内聚低耦合、可扩展、可靠、安全”等形容词；每个质量属性都要绑定场景、度量或验证证据。优缺点要结合本项目，而不是照搬教材表格。

## 常用知识点的工程化表达

- **架构风格/分层**：说明层的职责、依赖方向、接口契约和变更隔离；不要只画模块名。
- **组件/构件复用**：写标准接口、版本兼容、装配方式、替换成本和复用验证。
- **配置驱动/模型驱动**：写模型或配置的 schema、解析、静态校验、运行时调度和错误反馈。
- **需求与质量属性**：把性能、可靠性、安全、可维护性转成场景、阈值、优先级和验收方法。
- **软件测试**：区分单元、集成、系统测试；分别写输入空间、交互时序、端到端场景、预期结果和回归。
- **风险与项目管理**：写风险触发条件、影响、责任人、应对、监控和复盘，不写泛泛的“加强管理”。
- **数据与安全**：写数据来源、最小权限、脱敏/隔离、完整性校验、留痕和出域边界。
- **人工智能/LLM**：重点写上下文装配、提示约束、结构化输出、规则/工具校验、执行回放、人工复核和幻觉治理；不能把模型输出直接当测试结论。

## LLM/软件测试案例的可靠写法

若题目涉及 LLM，使用以下闭环：

1. 读取功能说明、接口契约、单位/采样率/初始化顺序和正反例。
2. 按单元、集成、系统层级分别设计提示和测试目标。
3. 强制生成 XML/JSON/CSV 等结构化产物，并限制枚举、范围、引用关系。
4. 用 schema、静态规则、工具调用和黄金样本校验；失败则回馈修正，不直接入库。
5. 执行测试并回放日志，比较预期与实际，人工复核物理边界和异常结果。
6. 报告覆盖率、生成耗时、缺陷发现、误报/漏报和数据安全边界。

明确写出模型局限：幻觉、输出漂移、领域规律掌握不足、接口版本变化、敏感数据风险。解决措施必须与局限一一对应。

## 文风、篇幅与真实性

- 采用第一人称工程叙事：“我负责……”“我们将……”，但避免虚构职位、客户、指标和标准。
- 每段只承担一个论点；先结论后细节，少用口号。
- 摘要交代时间、项目、问题、方法和结果；正文解释取舍；结语总结收益、认识和不足。
- 数字必须可解释（基线、口径、时间范围）；无法核实时用“约/显著”并说明依据，或留占位符。
- 符合题目字数和考试格式；写完后做字数统计和三问覆盖检查。

## 交付格式

根据用户请求选择：

- **提纲**：给出论点、段落目的、证据和待补事实。
- **草稿**：给出完整论文，并在不确定处用 `[待核实：...]` 标注。
- **批改**：按审题、结构、知识、工程性、逻辑、语言、真实性逐项指出问题，并提供替换句。
- **模拟评分**：先列评分依据，再给分项结果、失分风险和优先修改顺序。

未经用户要求，不把草稿写入学习数据库，也不把论文资料整书导入知识库。
